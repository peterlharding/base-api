# v0.7.0 - Referential integrity for the CRM tables

Released 2026-09-16.

The CRM tables shipped in 0.6.0 without foreign keys, so a reference column
accepted any bigint and nothing noticed when it pointed at nothing.
This release adds 25 constraints.

See [CHANGELOG.md](../CHANGELOG.md) for the itemised list.

## Upgrading

`make migrate`.

Unlike 0.6.0 there is a real upgrade path, and an existing database is
migrated in place.
The migration reconciles before it constrains: any reference that does not
resolve is set to NULL first.
That discards data, but only data that was already meaningless - a reference
to a row that is not there.

If you would rather see what will be discarded before running it, this
reports the same rows the migration will clear:

```sql
SELECT 'contact.account_id' AS col, count(*) FROM contact c
 WHERE c.account_id IS NOT NULL
   AND NOT EXISTS (SELECT 1 FROM account p WHERE p.id = c.account_id);
```

## What changed, and why

### ON DELETE SET NULL, not CASCADE or RESTRICT

Deleting a user orphans the records they owned rather than destroying them,
and deleting an account leaves its contacts intact but unlinked.
Nothing is ever lost as a side effect of deleting something else, which
matters while the API has no authentication and no soft-delete story.
Every column involved was already nullable, so nothing had to change.

The three self-references - `account.parent_id`, `contact.reports_to_id`,
`user_role.parent_role_id` - flatten rather than cascade.

### Deferrable, because two tables reference each other

`application_user.user_role_id` points at `user_role`, and
`user_role.forecast_user_id` points back.
No insertion order satisfies both while constraints are checked per
statement, which is why the sample data could not be loaded once the
constraints existed.

They are `DEFERRABLE INITIALLY IMMEDIATE`, so an ordinary request still
fails on the statement that caused it, with the constraint named.
A bulk load that cannot honour the ordering issues `SET CONSTRAINTS ALL
DEFERRED` inside its transaction, which `scripts/seed.py` now does.

### Twenty columns stay unconstrained

Deliberately, for three distinct reasons, all recorded in the migration:

- **polymorphic** - the target table is chosen by a sibling discriminator:
  `access.reference_id`, `note.parent_id`, `task.who_id`, `task.what_id`,
  `attachment.parent_id`
- **wrong type** - `event.account_id` and `event.owner_id` are `varchar(18)`
  on that table, and `audit_log.user_id` is varchar
- **no target table** - `application_user.profile_id`, and the opaque
  `*_ref` columns

A test pins that the polymorphic ones still accept any bigint, so the
asymmetry reads as a decision rather than an oversight.

### Constraints live in the migration only

Postgres has no `ADD CONSTRAINT IF NOT EXISTS`, so a constraint written into
`db/schema/create/*.sql` **and** added by a later migration is applied twice
on a fresh build, and the migration fails.
Constraints therefore live only in the revision that introduces them.
This corrects the rule in `CLAUDE.md`, which previously said a schema change
means editing the `.sql` file plus adding a migration - true for columns,
not for constraints.

## Known gaps

- **None of the 25 child columns is indexed.**
  Postgres does not create an index for a foreign key, so a parent delete
  scans each child table.
  Harmless at current volumes, worth addressing before they grow.
- Unknown fields in a request payload are still silently dropped rather than
  rejected with 422.
- `api_credentials`, `audit_log`, `instance_metadata`, `login_session`,
  `token_blacklist` and `user_role` have models but no endpoints, and the
  API still has no authentication.
