# v0.14.0 - Retention, and Python 3.12

Released 2026-09-18.

Three tables grew without bound.
Now there is a policy, and it is not the same policy for all three.

Not breaking. No migration.

See [CHANGELOG.md](../CHANGELOG.md) for the itemised list.

## Upgrading

```sh
git pull
uv sync
make prune-dry-run        # see what the policy would remove
make prune                # apply it
```

Nothing runs `make prune` on a schedule.
`scripts/prune.py` carries a cron line for a deployment that wants one.

## The policy

| table | pruned by | default |
| --- | --- | --- |
| `token_blacklist` | expiry | always |
| `login_session` | age, once the session has ended | 90 days |
| `audit_log` | age | **kept indefinitely** |

The differences are the point.

`token_blacklist` prunes by **expiry** because the row's purpose ends with
the token it revokes - after that the token fails validation on its own.
There is no decision to make, so no setting is offered.

`login_session` and `audit_log` prune by **age**, because they are history.
A record that somebody signed in stays true after the session ends, so how
long to keep it is a judgement, which is why both are settings.

A `login_session` that has **not** ended is never deleted, however old.
Removing the record of a session that still works would leave the API unable
to say who is connected.

`audit_log` defaults to `0`, meaning keep everything.
An audit trail that deletes itself on a timer is a weaker guarantee than one
that does not, and at one row per mutation it grows slowly enough that
deciding later is a real option.
The mechanism is present so that bounding it is `AUDIT_LOG_RETENTION_DAYS`
rather than new code.

## Python 3.12

`requires-python` drops from `>=3.14` to `>=3.12`, matching the deployment
target.

Verified rather than assumed.
Every file parses under `feature_version=(3, 12)`, there is no 3.13+ stdlib
or typing usage, and the full suite passes on a real 3.12 interpreter in a
separately resolved environment as well as on 3.14.
The API was also booted under 3.12 and exercised end to end - authenticate,
a protected read, a create, and the resulting audit entry.

There is no CI, so nothing checks 3.12 except deliberately.
`CLAUDE.md` says so; a note is weaker than an automated check, and this is
the second time the deployment has surfaced something this machine could not.

## One tool, not one per table

`scripts/prune.py` replaces `scripts/prune_blacklist.py` and handles all
three with `--dry-run` and `--only`.
`make prune-blacklist` still works, delegating - it was documented a day ago
and there is no reason to break it.

Logout continues to prune `token_blacklist` opportunistically, which covers
the ordinary case without anything scheduled.

## Also: a Docker prerequisite, written down

On Debian and Ubuntu the Docker CLI and the Compose plugin are separate
packages, so Compose can lag years behind while `docker --version` looks
current.
Docker Engine 29 refuses clients below API 1.44; Compose 2.18 asks for 1.42.

`doc/TESTING.md` now records the error, the three commands that isolate which
component is at fault, and how to run the suite without Compose at all -
`make test` only starts a container before `pytest`, so `pytest` alone works
once that container exists by any means.
