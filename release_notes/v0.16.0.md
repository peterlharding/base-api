# v0.16.0 - CORS

Released 2026-09-18.

A browser can now be told it may call this API.
It is not told so by default.

Not breaking. No migration.
An existing deployment behaves exactly as it did until `CORS_ORIGINS` is set.

See [CHANGELOG.md](../CHANGELOG.md) for the itemised list.

## Upgrading

```sh
git pull
uv sync
```

Then, only where a browser front end needs it, add to `.env`:

```sh
CORS_ORIGINS=http://localhost:5173,http://127.0.0.1:5173
```

Exact origins - scheme, host and port, no trailing slash.
`localhost` and `127.0.0.1` are different origins as far as a browser is
concerned, so list both if you use both.

Empty, which is the default and what every current deployment has, installs
no middleware at all.
The API was built for a server-to-server caller, which needs none.

## Checking it

```
$ curl -i -X OPTIONS http://127.0.0.1:8091/api/v1/users \
    -H "Origin: http://localhost:5173" \
    -H "Access-Control-Request-Method: POST" \
    -H "Access-Control-Request-Headers: authorization,content-type"

HTTP/1.1 200 OK
access-control-allow-origin: http://localhost:5173
access-control-allow-methods: GET, POST, PUT, DELETE, OPTIONS
access-control-allow-headers: ..., Authorization, ..., Content-Type
```

Note that this is a protected route and the preflight carries no token.
It has to work that way: a browser sends a preflight without credentials, so
a preflight that had to be authenticated could never succeed and every
cross-origin write would fail.
`configure_cors()` therefore runs before the router is included.

An origin that is not listed still gets a normal `200`, with no
`access-control-allow-origin` header.
The browser is what refuses to hand the response to the page - the API does
not pretend the request never happened.

## The wildcard

`CORS_ORIGINS=*` is accepted on dev, test and staging, with a warning in the
log.

On a `prod` release it raises at startup and the application does not come
up.
Every other origin check is a list that somebody maintains; `*` is the one
value that silently stops being one, and what it permits is any site on the
internet reading authenticated responses from a browser that holds a token.

Same reasoning as `handler.py` refusing the placeholder `JWT_SECRET` by name:
a default that merely looks wrong still works perfectly.

## Two decisions worth knowing

**No credentials.**
`allow_credentials` is off.
Authentication here is a bearer token in a header, which a browser sends
without `credentials: 'include'`.
Turning it on would attach cookies to cross-origin requests and buy nothing
this API uses.

**Methods and headers are listed, not `*`.**
The browser is told the real surface.
`tests/test_cors.py::test_every_method_the_api_serves_is_allowed` derives the
served methods from the live OpenAPI schema and checks them against the
allowed list, so a router that gains `PATCH` fails a test rather than a
preflight somebody has to debug from the network tab.

## A note for the front end

The client secret on `POST /auth/authenticate` is still HTTP Basic, and it
cannot ship in a JS bundle - anything sent to a browser is public.
CORS does not change that.
A browser client needs either a small proxy holding that credential or a
different rule for browser callers, and that decision is still open.
