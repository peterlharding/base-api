# v0.10.0 - Endpoints for the front end

Released 2026-09-17.

Three resources the React application needs: sign-in history, an activity
log, and a way to ask which backend it is talking to.

Not breaking. Existing endpoints are unchanged.

See [CHANGELOG.md](../CHANGELOG.md) for the itemised list.

## Upgrading

```sh
make migrate
```

Migration `0006` stamps the `instance_metadata` singleton, without which
`GET /api/v1/instance-metadata` returns 404.
It takes `release` from the new `RELEASE` setting (`dev`, `test`, `staging`
or `prod`, defaulting to `dev`) because a migration cannot know which
environment it is running against.
If a row is already present it is left alone.

## The three endpoints

| | methods | shape |
| --- | --- | --- |
| `/api/v1/login-sessions` | `GET` | list and by id |
| `/api/v1/audit-log` | `GET`, `POST` | list, by id, create |
| `/api/v1/instance-metadata` | `GET` | one object |

None of them is plain CRUD, and the asymmetries are deliberate.

### login-sessions is read-only

The API writes the row itself when it issues a token, and `refresh` advances
`last_seen`.
A front end that reports its own sessions can decline to, or report someone
else's, so the record is made where the facts are known.

Only a SHA-256 of the token is stored, and the endpoint does not return even
that: a leaked session table should not hand out working tokens.

Filters: `user_id`, and `active` for unrevoked and unexpired.

### audit-log is append-only

`GET` and `POST`; `PUT`, `PATCH` and `DELETE` return 405.
An audit trail that the parties it records can edit is not one.

`user_id` is taken from the bearer token.
Sending it in the payload is a 422 - a log that records whoever the caller
claims to be is worthless.

Filters: `application`, `event`, `user_id`.

### instance-metadata is a singleton

```json
{
  "release": "dev",
  "app_version": "v0.10.0",
  "db_version": "v0.7.1",
  "alembic_revision": "0006",
  "notes": "...",
  "updated_at": "..."
}
```

`release`, `db_version` and `notes` come from the row.
`app_version` is read from `pyproject.toml` and `alembic_revision` from
`alembic_version`, at request time - a version stamped into a row goes stale
the moment the application is upgraded without a migration, which is most
upgrades, and the front end wants to know what is actually serving it.

## Two bugs worth recording

**Sign-ins were not being recorded at all.** `ip_address` is `INET`, and
`request.client.host` is not always an address: a proxy may report a
hostname, and the test client reports a literal name.
The insert failed, and the recorder catches its own exceptions by design -
an audit trail that can refuse a sign-in is worse than one with a gap - so
the failure was invisible.
Non-addresses now go to `workstation`, which is free text.

**The list endpoint returned 500 against any real client.** `INET`
deserialises as an address object rather than a `str`, and the schema said
`str`.
The test suite did not catch it, because the test client only ever populates
`workstation` and leaves `ip_address` NULL, so the sign-in path alone never
exercised the column.
There is now a test that plants a real address.

## Also in this release

`tests/test_no_secret_logging.py` captures stdout, stderr and the logger
during a sign-in and asserts that the client secret, the user password, the
signing secret and the issued token appear in none of them.
Debug prints of the credentials object were reintroduced three times while
this work was in progress, and each one writes a plaintext password to
whatever collects process output.

The `jwt_secret` placeholder default is now rejected by name.
It is long enough to pass the length check, so without that a deployment
missing a `.env` would sign perfectly valid tokens using a string from the
repository.

## Known gaps

- **The API does not write `audit_log` itself.** The front end can post its
  own activity, but a create, update or delete through a CRUD route leaves no
  trace.
- **No logout.** `token_blacklist` is checked on every request and nothing
  writes to it.
- **`created_by_id` / `updated_by_id` are still NULL everywhere**, though the
  bearer dependency now yields the acting user.
- **Migrations have no tests.** Every test runs against a database already at
  head, so a migration that corrupts existing rows passes the suite.
