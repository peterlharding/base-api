# v0.6.0 - CRM schema and endpoints

Released 2026-09-16.

This release turns the API scaffold into a working CRM backend.
It is the largest change since the project began, and it is **breaking**:
the migration chain was rewritten and `application_user` was redesigned, so
an existing database cannot be migrated forward.

See [CHANGELOG.md](../CHANGELOG.md) for the itemised list.

## Upgrading

There is no upgrade path.
The chain that would have carried an existing database forward no longer
exists, so rebuild:

```sh
cd docker/db && make down && make up && make setup
cd ../.. && make migrate && make seed-reset
```

Nothing shipped in this project held production data, so the practical cost
is the dev database, which `make seed-reset` repopulates.

## What changed, and why

### Twelve CRM resources

`accounts`, `contacts`, `tasks`, `events`, `documents`, `notes`,
`opportunities`, `leads`, `quotes`, `access` and `attachments` join `users`
under `/api/v1`, for 24 routes.
Every one follows the shape `users.py` already had: page with `limit` and
`offset`, create, fetch-or-404, patch-style `PUT`, delete.

The parts that differ only by model moved to `app/api/v1/crud.py` rather than
being copied eleven times.
`commit()` there also translates constraint violations into 4xx instead of
letting them escape as a 500 - unique to 409, and foreign-key, not-null and
check to 400.

Three tables break the pattern and are worth knowing about:

- `access` has no audit columns at all, so no `created_at` / `updated_at` and
  no trigger.
- `quote.quoter` is `NOT NULL`, making it the only resource whose mandatory
  create field comes from the schema rather than an API-level choice.
  Its money columns are `numeric(12, 2)` and serialise as JSON strings, so
  precision survives.
- `event.account_id` and `event.owner_id` are `varchar(18)` on that table,
  not bigint as the same names are elsewhere.

### The schema is now owned by alembic alone

`make setup` creates the roles and an empty database; `make migrate` creates
every table.
That is the same path the test suite takes, so dev and test are built
identically - verified by diffing all 430 objects in both.

The previous arrangement had two sources of truth, and they had already
drifted: the bootstrap SQL produced a 37-column `application_user` against
the migrations' 38, which surfaced as a 500 on `/api/v1/users` while
`/health` stayed green.

`db/schema/create/*.sql` is therefore migration payload, not reference
material, and the `DROP TABLE IF EXISTS` headers are gone - a re-run would
otherwise have destroyed data.

### Sample data stays out of the chain

`db/schema/data/*.sql` loads through `make seed`, never a migration.
Migrations replay on every environment including production, the suite
truncates between tests so migration-seeded rows would not survive, and the
files assume ids that identity columns do not guarantee.

The loader refuses to run against non-empty tables; `make seed-reset`
truncates first.

## Known gaps

- The CRM tables declare **no foreign keys**, so `account_id`, `owner_id`,
  `parent_id` and the rest accept any bigint and nothing validates them.
- Unknown fields in a payload are silently dropped, so a client typo is
  either a confusing 400 or a silent success rather than a clear 422.
- `api_credentials`, `audit_log`, `instance_metadata`, `login_session`,
  `token_blacklist` and `user_role` have models but no endpoints.
