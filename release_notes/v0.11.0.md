# v0.11.0 - Record who wrote each row

Released 2026-09-17.

`created_by_id` and `updated_by_id` have existed on twelve tables since the
CRM schema landed, and every row had them NULL because the API had no concept
of a current user.
It does now, so they are filled in.

Not breaking. No migration.

See [CHANGELOG.md](../CHANGELOG.md) for the itemised list.

## What it does

```
POST /api/v1/accounts        as plh     -> created_by_id=2  updated_by_id=2
PUT  /api/v1/accounts/3      as admin   -> created_by_id=2  updated_by_id=1
```

`created_by_id` records who made the row and never moves.
`updated_by_id` follows whoever wrote last.

Both are readable on the response schemas and absent from the write schemas,
so sending them is a 422: the value comes from the bearer token or not at
all.
A log that records whoever the caller claims to be is worth nothing.

The twelve tables with the columns are stamped; `access`, `audit_log` and
`login_session` do not carry them and are untouched.

## Where it lives

In `crud.commit()`, which every write already funnels through.
One place to get right, and no route can quietly skip it.

`actor_id` is a **required** parameter rather than a defaulted one.
A default would mean a new endpoint could omit it and write rows with no
provenance, and nothing would say so.
Required means it fails at import.

## Two things worth knowing

**Contextvars do not work for this.** The tempting design is to set the user
in a contextvar from the bearer dependency and read it inside `commit()`,
leaving all thirty-nine routes untouched.
It does not work: a contextvar set inside a FastAPI dependency does not reach
the endpoint body, in either sync or async routes.
So write routes take `actor: ApplicationUser = Depends(jwt_bearer)` as a
value, and read routes keep `dependencies=[...]`.

**The parameter is `actor`, not `user`.** In `users.py` the entity being
written is itself a user:

```python
def create_user(..., user = Depends(jwt_bearer)):
    user = ApplicationUser(...)                     # shadows the dependency
    commit(db, ApplicationUser, _LABEL, user.id)    # the new row, not the caller
```

That recorded the new row's own id instead of the caller's - `None` before
the flush.
`users` is the only resource where the two names collide, and a parametrised
test across all twelve resources is what caught it.
A check of `accounts` alone would have passed.

## Known gaps

- **The API still does not write `audit_log` itself.** The front end can post
  its own activity, but a create or update through a CRUD route leaves no
  entry.
  The plumbing is now in place: `commit()` knows both the actor and the
  model.
- **No logout.** `token_blacklist` is checked on every request and nothing
  writes to it.
- **Migrations have no tests.** Every test runs against a database already at
  head, so a migration that corrupts existing rows passes the suite.
