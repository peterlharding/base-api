# v0.7.1 - Index the foreign key columns

Released 2026-09-17.

A follow-up to 0.7.0.
The foreign keys added there constrained the CRM tables correctly, but left
every child column unindexed.

See [CHANGELOG.md](../CHANGELOG.md) for the itemised list.

## Upgrading

`make migrate`.

Migration `0005` creates 25 indexes.
Nothing else changes: no columns, no constraints, no data.

The indexes are built inside the migration transaction, which takes a brief
exclusive lock on each table.
On the volumes this project currently holds that is imperceptible.
If you are running it against a large database and cannot take the lock, the
alternative is `CREATE INDEX CONCURRENTLY` outside a transaction - but that
cannot be driven from an alembic migration, and it can leave an invalid index
if it fails, so the transactional build is the right default until table size
says otherwise.

## Why

Postgres indexes the parent side of a foreign key, because it needs a unique
constraint there, but creates nothing on the child side.
Every `DELETE` on a parent therefore scanned each referencing table to find
the rows it had to set to NULL.
With 25 constraints that is up to 25 sequential scans per parent delete.

## What it is worth, measured

Deleting one account from `contact`, with and without
`contact_account_id_idx`:

| rows in `contact` | with index | without index |
| ----------------- | ---------- | ------------- |
| 50,000            | ~5 ms      | ~5 ms         |
| 1,000,000         | ~12 ms     | ~47 ms        |

At 50k the index is used but the scan is cheap enough that the `SET NULL`
update dominates, so the two are indistinguishable.
At 1M it is roughly 4x, and the gap widens with table size because the scan
is O(n) while the index lookup is not.

So this release changes nothing measurable at present volumes.
It is worth doing now because the cost of adding an index rises with the
table it sits on, and because a missing one is invisible until it is a
problem.

## Naming

`<table>_<column>_idx`, matching `login_session_user_id_idx` and
`token_blacklist_expiry_idx`, rather than SQLAlchemy's `ix_` default.
The indexes are declared in each model's `__table_args__` as well as the
migration, or `alembic revision --autogenerate` would propose dropping all
twenty-five.

## Known gaps

Unchanged from 0.7.0:

- Unknown fields in a request payload are silently dropped rather than
  rejected with 422.
- `api_credentials`, `audit_log`, `instance_metadata`, `login_session`,
  `token_blacklist` and `user_role` have models but no endpoints.
- The API has no authentication.
