# v0.12.0 - Logout

Released 2026-09-17.

`token_blacklist` has been checked on every request since 0.9.0, and nothing
ever wrote to it.
Now something does.

Not breaking. No migration.

See [CHANGELOG.md](../CHANGELOG.md) for the itemised list.

## Using it

```sh
curl -X POST http://127.0.0.1:8087/api/v1/auth/logout \
  -H "Authorization: Bearer $TOKEN"
```

Returns 204.
The token stops working immediately - not because the client discards it, but
because the server refuses it:

```
token GET /api/v1/users   ->  401  "Token has been revoked"
token POST /auth/refresh  ->  401  "Token has been revoked"
```

A second logout with the same token returns 401, which is less an error path
than proof the first one took effect.

## What it writes

`token_blacklist` gets the token's `jti`, the acting user, a reason of
`logout`, and the token's own expiry - so the row can be pruned once the
token would have lapsed anyway.

The matching `login_session` is stamped `revoked_at`, so the session list
shows what happened rather than a row that merely stops being refreshed.
It also drops out of `GET /api/v1/login-sessions?active=true`.

## One token, not all of them

Signing out on one device leaves other devices signed in.
Each token carries its own `jti`, so revoking one does not touch the rest.

There is a test pinning this, because the opposite behaviour is a defensible
choice that someone could later assume was already in place.
A "sign out everywhere" would be a separate endpoint.

## The fix that came with it

`refresh` does not go through the bearer dependency - it reads the
`Authorization` header itself - so it **never consulted the blacklist**.
A revoked token could have been exchanged for a fresh one, which would have
made logout decorative.

The blacklist is now checked in both places, and each was confirmed
load-bearing by disabling it in turn:

| check disabled | tests that failed |
| --- | --- |
| `refresh`'s lookup | `test_a_revoked_token_cannot_be_refreshed` |
| `bearer.resolve()`'s lookup | 3, including `test_the_token_stops_working` |

Both paths work perfectly on their own, which is why the gap was only visible
from the outside.

## Known gaps

- **Nothing prunes `token_blacklist`.** Rows carry an `expiry` precisely so
  they can be deleted once the token would have expired anyway, but no job
  does it.
  It grows one row per logout, indefinitely.
- **No revoke-all.** See above.
- **The API still does not write `audit_log` itself.**
