# v0.13.0 - The API writes its own audit trail

Released 2026-09-18.

**Breaking**, in two ways: the `audit_log` table is reshaped, and
`POST /api/v1/audit-log` is gone.

See [CHANGELOG.md](../CHANGELOG.md) for the itemised list.

## Upgrading

There is **no migration**.
The create SQL is edited in place, so the database has to be rebuilt:

```sh
cd docker/db && make down && make up && make setup
cd ../.. && make migrate && make seed-reset
```

This is deliberate for a project with no deployments and no data in the
table.
The consequence is worth stating plainly: an older tag no longer reproduces
what a fresh build gives, and a database already at revision `0002` keeps the
old shape until rebuilt.
Once there is data anywhere that matters, schema changes want a migration
again.

## What the table looks like now

```sql
audit_log
  id              bigint identity
  application     varchar(32)  NOT NULL      -- 'base_api'
  action          varchar(32)  NOT NULL      -- create | update | delete
  reference_type  varchar(64)  NOT NULL      -- 'account', 'contact'
  reference_id    bigint                     -- nullable
  description     text         NOT NULL DEFAULT ''
  user_id         varchar(50)  NOT NULL
  created_at      timestamptz  NOT NULL DEFAULT now()
```

`reference_type` is the table name rather than an integer code.
The integer needed a mapping that existed nowhere, so it would have had to be
invented and then kept in step with the schema forever; the table name is
already on every model as `__tablename__`.

`reference_id` is kept.
"Who changed account 42" is the question the table exists to answer, and
without the id the best available answer is "somebody updated an account at
10:03", correlated by timestamp against `updated_at`.
That falls apart as soon as two people are working.

`reference` is dropped: a human-readable label duplicates data one join away
and goes stale the moment the row is renamed.

## Where entries come from

`crud.commit()` - the same place the `created_by_id` stamps are applied, and
the only point every mutation passes through.

The alternative was a call in each endpoint, which would have been
thirty-nine more places to forget, and a route that forgets is silently
unaudited with nothing to say so.

Because it reads the session rather than the request, `action` describes what
the database did:

```
create  account  id=3  ''
update  account  id=3  'changed: billing_city, industry'
delete  account  id=3  ''
```

Between the update and the delete above there was a second `PUT` setting
`industry` to the value it already held, and a `GET` on the collection.
Neither appears.
The log describes the data, not the request.

An update's `description` lists the columns that changed, not their values.
An audit table holding before and after for every column becomes a second
copy of the database, including the parts nobody wanted duplicated.

## Mutations only

Reads are not recorded.
On a CRM the list endpoints would produce more rows than everything else
combined and the signal drowns.

`action` is free text rather than a constrained set, so `login`, `export` or
`convert-lead` can be added later without touching the schema.

## POST is removed

The API is the only writer.
An entry a client can compose is one it can fabricate, omit, or attribute to
somebody else.

If the front end needs to record something the backend cannot see, that is a
reason to add an action the backend performs - not to reopen the table to
arbitrary writes.

## Verified to fail when it should

| broken how | result |
| --- | --- |
| auditing disabled entirely | 6 of 11 tests fail |
| no-op detection removed | `test_an_update_that_changes_nothing_records_nothing` fails |

A sweep over all thirteen mutating resources asserts none is unaudited, so a
resource added later is covered without extending the file.
Two behaviours are pinned because they are decisions rather than accidents: a
rejected write leaves no entry, since the entry shares the operation's
transaction, and the audit trail does not audit itself.

## Known gaps

- **Nothing prunes `audit_log`.** One row per mutation, by design.
  How long to keep them is a retention decision rather than a cleanup one,
  and it now applies to three tables: this, `login_session`, and
  `token_blacklist` on a schedule.
- **No revoke-all.**
