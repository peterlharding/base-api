# v0.11.1 - Test migrations against data

Released 2026-09-17.

Tests only.
No migration, no schema change, no behaviour change.

See [CHANGELOG.md](../CHANGELOG.md) for the itemised list.

## The gap

Every test in this suite ran against a database already at head.
A migration that corrupts existing rows passes all of them, because no test
ever holds data across an upgrade.

That is not a theoretical hole.
Migration `0004` shipped in v0.7.0 with an unaliased subquery in its
reconciliation step: for the four self-referencing foreign keys the inner
`FROM` shadowed the outer table, every row looked dangling, and valid values
were cleared.
222 tests stayed green.
It was caught because a seeded `parent_role_id` looked wrong by eye.

## What was added

`tests/test_migrations.py` plants rows at one revision, upgrades, and asserts
what survived:

```python
def test_something(migrate):
    migrate.to("0003")
    with migrate.session() as s: ...   # plant
    migrate.to("0004")
    with migrate.session() as s: ...   # assert
```

Fifteen tests covering:

- the `0004` regression directly
- that `0004` still clears *genuinely* dangling references, so the
  reconciliation is not merely disabled
- that `0004` never touches a primary key - an early draft parsed the
  constraint names with a greedy regex and produced `UPDATE ... SET id = NULL`
- that every revision steps back exactly one and forward again, parametrised,
  so a broken downgrade names the revision at fault
- that base to head to base leaves no tables behind
- that `0005` leaves no unindexed foreign key column
- that `0006` stamps a row when there is none and declines to overwrite one
- that data planted at `0003` is intact at head
- that the `set_updated_at` trigger still fires after a full migration

The revision list comes from alembic's `ScriptDirectory`, so a new migration
is covered without editing the file.
A guard asserts the discovery found at least six, so it cannot silently match
nothing.

## Isolation

These tests move the schema version around, so they cannot share the database
the rest of the suite uses.
They get a scratch database created and dropped per session.

`db/alembic/env.py` now honours a `sqlalchemy.url` the caller has already
pinned, falling back to application settings as before.
Without that it rebuilt the URL from settings and pointed the tests straight
back at the shared database.

## Verified to fail when they should

| bug reintroduced | test that failed |
| --- | --- |
| `0004` unaliased self-reference | `test_0004_preserves_valid_self_references` |
| `0005` downgrade misses an index | `test_each_revision_steps_back_and_forward[4]` |
| `0006` overwrites an existing row | `test_0006_is_idempotent_and_respects_an_existing_row` |

A test that has never been seen to fail is a test nobody should trust.

## Cost

The suite goes from 34 to 43 seconds, and from 432 to 447 tests.

## Writing migrations from here

A migration that changes data wants a test that plants rows at the previous
revision, upgrades, and asserts what survived.
`doc/TESTING.md` has the shape.
