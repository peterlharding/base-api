# v0.8.1 - user_role endpoints, and a data-loss fix in migration 0004

Released 2026-09-17.

**If you upgraded a populated database through migration `0004` (shipped in
v0.7.0), read the fix below - it silently discarded data, and this release
stops it happening again but cannot recover what was lost.**

See [CHANGELOG.md](../CHANGELOG.md) for the itemised list.

## Upgrading

No migration to run.
`0004` is edited in place rather than superseded, because the correction is
to a step that only executes once, and a database already past `0004` will
never re-run it.

`git pull` and restart.

## The fix

Migration `0004` reconciles unresolvable references to NULL before adding
each foreign key, so that a populated database can be upgraded in place.
For self-referencing tables it generated this:

```sql
UPDATE user_role SET parent_role_id = NULL
 WHERE parent_role_id IS NOT NULL
   AND NOT EXISTS (SELECT 1 FROM user_role
                    WHERE user_role.id = user_role.parent_role_id)
```

The inner `FROM user_role` shadows the outer one, so the subquery compares
each row against **itself** rather than correlating to the row being updated.
No row satisfies `id = parent_role_id`, so `NOT EXISTS` is true for every
row, and the column is cleared wholesale.

| row | `parent_role_id` | 0004 said | truth |
| --- | ---------------- | --------- | ----- |
| 1   | NULL             | dangling  | dangling |
| 2   | 1 (valid)        | dangling  | **not dangling** |

Both tables are now aliased.

### What was affected

The four self-references only:

- `account.parent_id`
- `contact.reports_to_id`
- `user_role.parent_role_id`
- `application_user.delegated_approver_id`

The other twenty-one constraints were never affected, because parent and
child are different tables and nothing shadows.

A **fresh build was never affected** either: `0004` runs immediately after
`0003` on empty tables, so there is nothing to discard.
The damage only occurs when upgrading a database that already holds data -
precisely the case the reconciliation exists to serve.

### Recovering

The values cannot be recovered from the database; they were overwritten with
NULL and nothing records the previous state.
Restore them from wherever the data originally came from.
Sample data comes back with `make seed-reset`.

### How it was found, and the gap it exposes

Not by the test suite.
It surfaced while exercising the new `user_role` endpoints against the dev
database: the seeded `Sales Manager` returned `parent_role_id: null`, where
the seed file gives it `1`.

All 222 tests pass against the buggy migration, because every test runs
against a database already at head.
A migration that corrupts existing rows is invisible to the entire suite.

data, upgrades and asserts.
That gap is the more important finding than the individual bug.
