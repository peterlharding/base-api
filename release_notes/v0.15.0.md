# v0.15.0 - Revoke all

Released 2026-09-18.

Logout revokes the token the request was made with.
This revokes every token the user holds, on every device, which is what a
lost laptop or a shoulder-surfed password actually calls for.

Not breaking. **One migration** (`0007`).

See [CHANGELOG.md](../CHANGELOG.md) for the itemised list.

## Upgrading

```sh
git pull
uv sync
make migrate
```

`0007` adds one nullable column.
It touches no existing data, and every row comes out of it with nothing
revoked.

## Using it

```sh
curl -X POST https://host/api/v1/auth/revoke-all \
     -H "Authorization: Bearer $TOKEN"
```

```json
{"revoked_before": "2026-09-18T04:12:55.318442Z", "sessions_ended": 3}
```

The token that made the call is revoked too.
That is the honest reading of "revoke all", and sparing the current device
would be a second rule to get wrong at the moment it matters most.
Sign in again to carry on.

## Why a cutoff and not a blacklist

The obvious implementation is to add every outstanding token to
`token_blacklist`, which already exists and already works.
It cannot be done.

`token_blacklist` is keyed on `jti`, and the only place a `jti` is ever
written down is the blacklist itself.
`login_session` stores a SHA-256 of the token rather than its id, so it
cannot produce one.
And `refresh` mints a token without writing a session row at all, so a token
obtained that way leaves no record anywhere in the database.

So there is no query that returns "every token this user currently holds".
Anything built on the records that do exist would revoke the tokens it knew
about and quietly miss the rest - including, in the refresh case, the ones an
attacker is most likely to be holding.

`application_user.tokens_revoked_before` sidesteps the problem.
It is compared against `iat`, a claim every token already carries, so a token
does not have to have been seen to be revoked.
One timestamp, no rows, and nothing to keep in step.

`tests/test_revoke_all.py::test_a_refreshed_token_stops_working` pins the case
that motivated the design.

## Two places, again

The cutoff is enforced in `bearer.resolve()` and, separately, in `refresh`.

This mirrors the blacklist and is load-bearing for the same reason: `refresh`
reads the `Authorization` header itself rather than going through the bearer
dependency, so a check only in the dependency would let a revoked token be
walked straight back into a working one.

Both checks were verified by removing them one at a time and confirming which
test went red.

## A note on `iat`

Tokens now carry a fractional `iat`.

RFC 7519 allows a non-integer NumericDate, and the precision matters here:
the cutoff is a `timestamptz` with microseconds, and at whole-second `iat`
resolution a token minted in the same second as a revoke-all lands on either
side of it depending on where the truncation falls.

Tokens issued before this release carry an integer `iat`.
They still compare correctly - truncation rounds towards the past, so an old
token can only look older than it was, which errs towards revoking rather
than away from it.

## Sessions

`revoke-all` stamps `revoked_at` on the user's open `login_session` rows, so
the session list reflects what happened rather than showing sessions that
quietly stopped being refreshed.

Sessions already revoked at logout keep their original timestamp - that is
when *that* session ended, and rewriting it would lose the fact.

## Migration `0007`

The column is declared in `db/schema/create/application_user.sql` **and**
added by the migration, with `ADD COLUMN IF NOT EXISTS`.

A fresh build gets it from the create script in `0001` and reaches `0007`
with the work already done; a deployed database gets it from the migration.
This is the opposite of the rule for constraints, which live only in the
migration because Postgres has no `ADD CONSTRAINT IF NOT EXISTS`.

Both paths are tested.
Only one of them is what your server will do.
